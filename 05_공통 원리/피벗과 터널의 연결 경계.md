# 피벗과 터널의 연결 경계

## 핵심 개념

피벗은 공격 호스트에 없던 네트워크 경로를 중간 호스트의 도달성으로 대신 만드는 작업입니다. 하나의 “터널”처럼 보여도 실제로는 진입 listener, 제어·전송 연결, 중간 호스트의 egress 연결, 최종 서비스와 애플리케이션이 연속된 경계를 이룹니다. 앞 경계의 성공은 다음 경계가 실행될 조건일 뿐 최종 접근을 보장하지 않습니다.

피벗, 터널링과 lateral movement는 같은 결과를 뜻하지 않습니다. 피벗은 중간 호스트를 이용해 없던 네트워크 도달성을 만들고, 터널링은 그 경로를 다른 전송 채널 안에 실어 구현하는 방식입니다. Lateral movement는 확보한 계정·세션·신뢰 관계로 다른 호스트나 서비스의 실행 권한을 얻는 행동입니다. 따라서 터널로 로그인 화면이 보이는 상태는 피벗 경로가 열린 것이며, 그 서비스에 인증하고 새 호스트의 세션을 얻었을 때 lateral movement 결과를 별도로 판정합니다.

| 구성 요소 | 역할 | 확인되는 상태 |
|---|---|---|
| 최종 클라이언트 | 브라우저·SMB·RDP·Nmap처럼 실제 프로토콜 요청 생성 | proxy·route를 사용하는지와 서비스 응답 |
| 진입 listener | 로컬 포트, SOCKS 포트 또는 TUN interface로 트래픽을 받음 | 지정 주소·포트 또는 interface가 존재함 |
| 애플리케이션 proxy hook | SOCKS를 지원하거나 ProxyChains로 가로챈 프로세스의 연결을 proxy listener로 보냄 | 해당 프로세스가 proxy를 실제 사용했는지 |
| 프레임워크 내부 route | Metasploit 같은 프레임워크 모듈의 연결을 특정 session으로 보냄 | 프레임워크 내부 모듈에만 적용되는 route와 session 대응 |
| 로컬 firewall interception | sshuttle처럼 선택한 목적지 트래픽을 로컬 firewall 규칙으로 사용자 공간 relay에 넘김 | 규칙과 일치한 로컬 TCP 흐름, 선택한 backend의 지원 범위 |
| OS kernel route와 TUN | route가 선택한 packet을 TUN interface로 보냄 | route 대상 CIDR, TUN과 agent session의 대응 |
| 제어·전송 연결 | SSH·Chisel·Ligolo agent처럼 공격 호스트와 피벗을 연결 | 세션 연결과 유지 상태 |
| 피벗 egress | 피벗 호스트에서 최종 주소·포트로 새 연결을 만듦 | 피벗의 route·DNS·방화벽 기준 도달성 |
| 최종 서비스 | TCP/UDP listener와 인증·인가 수행 | 배너, 인증 결과와 허용 행동 |

## 동작 원리

고정 포트 포워딩은 미리 정한 한 연결을 전달합니다. Local forward에서는 공격 호스트의 listener가 연결을 받아 전송 채널로 보내고, 피벗 쪽이 정해진 `<INTERNAL_IP>:<PORT>`로 연결합니다. Reverse forward에서는 listener가 피벗 또는 원격 쪽에 생기고, 들어온 연결이 반대편의 정해진 목적지로 돌아옵니다. 어느 쪽이 `listen`하고 어느 쪽이 `connect`하는지가 방화벽과 bind 조건을 결정합니다.

`reverse`라는 이름만으로 방향을 결정하지 않습니다. 다음 세 축을 각각 적어야 합니다.

| 방향 축 | 확인할 질문 | 대표 예 |
|---|---|---|
| 제어 연결 시작 주체 | client·agent·SSH client 중 누가 server로 먼저 연결하는가 | Chisel reverse SOCKS와 rpivot은 피벗 client가 공격 호스트 server로 연결함 |
| 진입 listener 위치 | 최종 애플리케이션이나 callback이 어느 호스트의 포트에 연결하는가 | Chisel reverse SOCKS·rpivot은 공격 호스트 SOCKS, SSH `-R`·Meterpreter `portfwd -R`은 원격·피벗 쪽 listener |
| 최종 connect 목적지와 실행 측 | listener로 들어온 연결을 어느 쪽이 어떤 목적지로 새로 연결하는가 | SOCKS는 피벗 쪽이 요청 목적지로, SSH `-R`은 SSH client 쪽이 지정 목적지로 연결함 |

따라서 SSH `-R`, Chisel `R:<PORT>:socks`, rpivot의 `reverse`와 Meterpreter `portfwd -R`은 모두 이름에 reverse가 들어갈 수 있지만 같은 listener·connect 배치를 뜻하지 않습니다. 각 실전 문서의 실제 인자와 양쪽 socket을 기준으로 판단합니다.

동적 포워딩은 진입점이 SOCKS proxy입니다. 최종 클라이언트가 매 연결마다 목적지 주소·포트를 SOCKS 요청에 넣고, 터널의 원격 쪽이 그 목적지로 연결합니다. SOCKS listener가 열렸어도 애플리케이션이 proxy를 사용하지 않으면 트래픽은 터널에 들어가지 않습니다. hostname을 넘길지 로컬에서 먼저 해석할지도 ProxyChains의 `proxy_dns`와 클라이언트 동작에 따라 달라집니다.

TUN 기반 피벗은 애플리케이션별 proxy 대신 운영체제 route가 packet을 TUN interface로 보냅니다. Ligolo-ng 같은 구현은 그 packet을 agent 쪽의 소켓 연결로 변환합니다. 따라서 TUN 존재, 해당 CIDR route, 선택된 agent tunnel과 agent의 최종 도달성이 모두 필요합니다. 이 모델은 일반 Ethernet bridge와 같지 않으며, agent가 raw packet을 그대로 내보내는지 또는 TCP connect 등으로 변환하는지는 도구 구현과 스캔 방식 선택에 영향을 줍니다.

### 경로가 자동 적용되는 범위

| 적용 방식 | 자동으로 경로를 쓰는 client | 기본적으로 확인할 protocol·이름 해석 경계 |
|---|---|---|
| 애플리케이션 proxy hook | proxy 주소를 직접 설정했거나 ProxyChains가 hook한 해당 process | 주로 TCP connect. hostname을 proxy에 넘길지 로컬에서 해석할지는 client와 `proxy_dns` 설정에 따름 |
| 프레임워크 내부 route | route를 조회하는 해당 프레임워크 모듈 | 외부 Nmap·브라우저에는 자동 적용되지 않음. 외부 client에는 별도 SOCKS listener와 proxy hook 필요 |
| firewall interception | 선택한 network namespace에서 규칙과 일치하는 로컬 process | sshuttle 기본 경로는 TCP 중심이며 UDP·ICMP는 선택 backend와 별도 조건을 확인 |
| kernel route + TUN | 운영체제 route를 따르는 같은 namespace의 일반 client | route가 packet을 TUN으로 보낸다는 사실과 agent 구현이 TCP·UDP·raw·ICMP를 처리하는 범위는 별도 |

이 표는 도달성 선택 기준이며 도구별 지원 계약을 대신하지 않습니다. 예를 들어 `route print`에 Metasploit route가 있어도 일반 shell의 `nmap`은 그 route를 자동 사용하지 않고, TUN route가 있어도 Ligolo-ng가 raw packet을 그대로 전달한다고 가정해 SYN scan 성공을 보장하지 않습니다.

다중 홉에서는 한 agent가 연 listener로 다음 agent의 제어 연결을 상위 proxy까지 relay할 수 있습니다. 이때 하위 agent는 `하위 호스트 → 직전 홉 listener → 상위 전송 연결 → proxy` 전체에 의존합니다. 중간 listener나 상위 agent를 먼저 종료하면 더 깊은 호스트의 원격 정리·상태 확인 경로도 함께 사라지는 이유입니다.

## 연결 방식에 따른 선택

| 필요한 경로 | 적합한 진입 방식 | 선택 조건 |
|---|---|---|
| 내부 서비스 한 개 | Local 고정 forward | 목적지와 포트가 이미 정해졌고 하나의 로컬 포트로 충분함 |
| 여러 TCP 서비스 | SOCKS dynamic forward | 최종 도구가 SOCKS/ProxyChains를 사용할 수 있고 TCP connect 방식이 적합함 |
| 내부에서 외부 listener로 callback | Reverse forward | 내부 호스트가 공격 호스트에 직접 연결하지 못하고 피벗 bind 포트에는 연결 가능함 |
| 여러 도구가 내부 CIDR을 직접 사용 | TUN과 route | 공격 호스트에서 TUN 생성 권한이 있고 도구의 지원 프로토콜 범위가 목표와 맞음 |
| 다음 agent가 상위 proxy에 직접 도달하지 못함 | 중간 agent listener relay | 각 하위 호스트가 직전 홉 listener에는 연결할 수 있음 |

[[SSH 포트 포워딩 피벗팅]]과 [[Chisel SOCKS 터널링]]은 고정·동적 listener 경계를 실제 명령으로 구현하고, [[Meterpreter 라우팅과 포트 포워딩]]은 프레임워크 내부 route와 외부 client용 SOCKS job을 구분합니다. [[sshuttle SSH 피벗팅]]은 로컬 firewall interception을, [[TUN 라우팅 피벗 구성]]은 kernel route와 TUN을 사용합니다. [[피벗팅 경로 식별과 내부망 열거]]는 이런 구현을 선택하기 전에 피벗 호스트 자체의 egress 도달성을 확인하는 단계입니다.

## 실전에서의 해석

| 관찰한 결과 | 확정할 수 있는 것 | 아직 확인할 경계 |
|---|---|---|
| client·agent가 proxy/server에 연결됨 | 제어·전송 채널 성립 | 진입 listener, route와 최종 대상 도달성 |
| 로컬 SOCKS·forward listener가 열림 | 진입점 생성 | 최종 애플리케이션의 proxy 사용과 피벗 egress |
| 피벗 호스트에서 대상 포트 연결 성공 | 피벗 egress baseline | 터널을 통과한 클라이언트 연결 |
| ProxyChains 체인 `OK` 또는 TUN 경유 TCP 응답 | 해당 목적지까지 데이터 경로 성립 | 서비스 인증과 허용 행동 |
| 로그인 화면·배너 표시 | 서비스 프로토콜 도달 | credential 유효성, 세션과 권한 |
| 인증 성공 | 해당 서비스의 identity 확인 | 파일 읽기·쓰기, 명령 실행과 관리자 권한 |

실패는 최종 오류에서 거꾸로 추측하지 않고 애플리케이션→proxy hook/route→진입 listener→전송 연결→피벗 egress→서비스 순으로 처음 끊긴 경계를 찾습니다. 예를 들어 피벗의 직접 `nc`도 실패하면 ProxyChains 설정을 바꿀 문제가 아니고, 직접 연결은 되지만 ProxyChains 로그가 전혀 없으면 대상 방화벽보다 애플리케이션 hook을 먼저 확인합니다.

## 관측과 통제가 나타나는 경계

터널은 내부 프로토콜을 다른 전송 안에 넣지만 모든 흔적을 하나로 합치지는 않습니다. 최종 클라이언트와 피벗 호스트에는 proxy를 사용하는 애플리케이션, 새 listener·route·interface, 터널 프로세스와 목적지 연결이 각각 남습니다. 중간 네트워크에서는 내부 payload가 암호화될 수 있어도 어느 호스트가 어느 주소·포트로 연결했는지, 연결 시간·전송량·반복 주기와 사용 포트는 별도 관찰 대상입니다. 따라서 암호화된 SSH·TLS·DNS 터널이라는 사실만으로 해당 연결이 정상 트래픽과 구분되지 않는다고 단정할 수 없습니다.

각 통제는 서로 다른 경계에서 실패를 만듭니다. 애플리케이션 allowlist나 실행 제어는 터널 프로세스 시작을 막고, host firewall은 listener bind 또는 피벗 egress를, network segmentation과 egress filtering은 제어 연결이나 최종 서비스 연결을 제한합니다. DNS resolver 제한은 대상이 권한 있는 domain을 재귀 질의하는 경로와 공격자 server로 직접 UDP 질의하는 경로에 서로 다르게 작용합니다. 어느 통제가 유효했는지는 최종 timeout 하나가 아니라 해당 경계의 process·socket·route와 양쪽 flow를 대조해 판단합니다.

탐지 관점에서도 단일 지표는 충분하지 않습니다. 승인되지 않은 `ssh`·`plink`·`socat`·agent process, 예상하지 않은 listen/connect 관계, 서비스 관행과 맞지 않는 port·protocol 조합, DNS·proxy 연결의 반복 패턴은 조사할 상관 단서입니다. 정상 관리 도구도 같은 형태를 만들 수 있으므로 자산·승인된 원격 관리 경로·평상시 flow 기준선과 결합해야 합니다. 이 관계는 터널을 실제로 실행할 때도 어떤 host의 어떤 process·listener·route가 이번 작업에 속하는지 먼저 기록해야 정확히 복구할 수 있는 이유입니다.

복구할 때는 의존 방향을 반대로 따릅니다. 연결이 살아 있을 때 가장 깊은 agent와 그 상태를 먼저 정리하고 중간 listener·agent, 공격 호스트의 route·TUN·proxy를 뒤에 정리합니다. 연결이 이미 끊겼다면 하위 프로세스·파일이 없어졌다고 추정하지 않고 독립 접근으로 확인할 때까지 원격 정리 상태를 미확인으로 남깁니다. 구체적인 PID·listener ID·route와 복구 명령은 각 실전 문서에 둡니다.
