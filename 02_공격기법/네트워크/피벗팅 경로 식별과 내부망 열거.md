# 피벗팅 경로 식별과 내부망 열거

## 한 줄 판단

공격 호스트에서 직접 도달하지 못하는 내부 대역이 의심되고 `<PIVOT_IP>`의 셸 또는 원격 명령 실행을 보유했으면, 피벗 호스트의 인터페이스·route와 `<INTERNAL_IP>:<PORT>` 연결을 확인해 터널이 필요한 경계와 다음 내부 서비스 후보를 정한다.

## 사용할 때

- 현재 네트워크 위치: 공격 호스트에서는 `<INTERNAL_CIDR>` 또는 `<INTERNAL_IP>:<PORT>`에 직접 연결할 수 없고, 셸을 보유한 `<PIVOT_IP>`가 외부 측 네트워크와 다른 서브넷에 연결된 것으로 보인다.
- 명령 실행 위치: `ip addr`, `ip route`, `ipconfig`, `route print`와 내부 포트 확인 명령은 피벗 호스트에서 실행한다. 터널 구성 뒤 비교 명령은 공격 호스트에서 실행한다.
- 보유 계정·피벗 세션: 피벗 호스트의 현재 셸 또는 원격 명령 실행을 유지하고 있어야 한다. 별도 내부 서비스 credential이나 Kerberos ticket이 없어도 네트워크 경로 식별은 가능하다.
- 현재 권한: 관리자/root 권한이 필수는 아니지만 현재 계정으로 인터페이스·route·DNS 정보를 읽고 내부 대상에 TCP 연결을 시도할 수 있어야 한다.
- 지금 가능한 행동: 피벗 호스트에서 내부 CIDR과 대상 후보를 찾고 `<INTERNAL_IP>:<PORT>` 기준선을 검증한 뒤, 확인된 연결 방향에 맞는 터널링 기법을 선택한다.
- 성공 범위: 피벗 호스트에서 내부 TCP 서비스까지 도달하는 경로와 터널이 필요한 경계를 얻는다. 이 단계만으로 공격 호스트의 내부 접근, 서비스 인증, 원격 명령 실행이나 관리자 권한을 얻은 것은 아니다.

## 전제 조건

| 확인할 것 | 필요한 상태 | 확인 방법 | 미충족 시 다음 확인 |
|---|---|---|---|
| 명령 실행 위치와 네트워크 경로 | `<PIVOT_IP>`의 셸 또는 원격 명령 실행이 유지되고 공격 호스트와 다른 내부 route 단서가 있음 | `whoami` 또는 `id`, `hostname`, 인터페이스와 route 확인 | 세션 재연결, 다른 NIC·VPN·container route와 다른 피벗 후보 확인 |
| 현재 계정 또는 인증 수단 | 피벗 호스트의 현재 사용자 세션 | `whoami`, `id` | 실행 계정, 세션 종류와 명령 제한 확인 |
| 현재 권한 | 현재 계정으로 네트워크 구성 조회와 내부 TCP 연결 시도 가능 | `ip route`, `route print`, `nc -vz` 실행 | 제한된 shell, 명령 존재 여부와 필요한 로컬 권한 확인 |
| 공격 대상의 조건 | ARP, route, DNS·hosts 또는 서비스 설정에서 `<INTERNAL_IP>:<PORT>` 후보 확인 | 각 단서의 주소·CIDR·hostname과 서비스 포트를 교차 확인 | CIDR 추정 범위와 대상 역할을 다시 좁힘 |
| 필요한 파일·목록·주소 | 외부 인터페이스, 내부 인터페이스, `<INTERNAL_CIDR>`, `<INTERNAL_IP>`, `<PORT>` | 공격 호스트와 피벗 호스트의 route를 비교 | 같은 주소가 어느 인터페이스·호스트 관점인지 다시 기록 |

## 실행

### 선택 기준
| 단서 | 의미 | 다음 행동 |
|---|---|---|
| 인터페이스가 2개 이상 | 피벗 호스트가 다른 네트워크에 붙어 있음 | 내부 CIDR을 파악하고 TCP 연결 테스트 |
| 내부 CIDR은 알지만 응답 호스트를 모름 | 피벗 호스트에서 ICMP sweep 가능 여부 확인 필요 | [[ICMP 기반 내부 호스트 확인]] |
| 내부망 route 존재 | 해당 대역으로 패킷 전달 가능 | `nc`, `nmap -sT`, 서비스 클라이언트로 확인 |
| ICMP만 가능하거나 TCP가 제한됨 | 일반 SSH/SOCKS가 막힐 수 있음 | [[ptunnel-ng ICMP 터널링]] 검토 |
| DNS 질의만 외부로 나감 | C2/터널 경로가 DNS로 제한될 수 있음 | [[dnscat2 DNS 터널링]] 검토 |
| RDP 세션은 가능하지만 SSH가 없음 | Windows 기반 피벗이 필요 | [[SocksOverRDP RDP 터널링]], [[Windows Netsh Portproxy 포트 포워딩]] 검토 |

### 절차
1. 피벗 호스트에서 현재 Identity, 권한과 호스트 역할을 확인한다.
2. 피벗 호스트의 인터페이스와 라우팅 테이블에서 공격 호스트가 직접 보지 못하는 `<INTERNAL_CIDR>`을 찾는다.
3. 내부 대상 주소가 아직 없으면 [[ICMP 기반 내부 호스트 확인]]으로 응답 호스트 후보를 얻고, ICMP 무응답 주소도 다른 단서가 있으면 유지한다.
4. 피벗 호스트에서 `<INTERNAL_IP>:<PORT>`로 직접 연결 가능한지 확인한다.
5. 공격 호스트에서도 같은 내부 포트를 직접 확인해 어느 구간에서 연결이 끊기는지 비교한다.
6. 접근 방향에 맞춰 SSH, Chisel, Meterpreter, Netsh, ICMP/DNS 터널 중 하나를 고른다.
7. 터널 생성 후 공격 호스트에서 같은 내부 대상의 TCP 또는 서비스 응답이 나타나는지 검증한다.

### Linux 피벗 호스트 네트워크 확인

```bash
id
hostname
ip addr
ip route
ss -tulpen
```

확인할 출력:

- 공격 호스트가 직접 볼 수 없는 `<INTERNAL_CIDR>`과 해당 route의 인터페이스·gateway.
- 피벗 호스트의 listener와 피벗 뒤 `<INTERNAL_IP>:<PORT>` 후보를 구분한다.

### Windows 피벗 호스트 네트워크 확인

```cmd
whoami
hostname
ipconfig /all
route print
netstat -ano
```

확인할 출력:

- 피벗 호스트 관점의 내부 DNS, gateway, 추가 NIC와 `<INTERNAL_IP>:3389/5985/5986/445` 같은 후속 접근 후보. 포트 응답은 다음 단계에서 따로 검증한다.

### 피벗 호스트에서 내부 포트 연결 확인

```bash
nc -vz <INTERNAL_IP> <PORT>
```

확인할 출력:

- `succeeded`, `open`, 서비스 배너: 피벗 호스트에서 `<INTERNAL_IP>:<PORT>`까지 TCP로 도달했다. 아직 공격 호스트 경로와 서비스 인증은 확보되지 않았다.
- `timed out`, `refused`: 대상 포트, 방화벽, 내부 route와 listener 상태를 구분해 다시 확인한다.

## 관찰과 상태 전환

| 관찰 | 판단 | 결과 상태 | 다음 행동 |
|---|---|---|---|
| 추가 NIC·route·내부 DNS가 확인됨 | 피벗 호스트에 연결된 내부 대역 후보가 있음 | 내부 CIDR과 대상 후보 확보 | 피벗 호스트에서 `<INTERNAL_IP>:<PORT>`를 직접 확인 |
| 피벗 호스트의 `nc -vz`가 `succeeded` 또는 `open`을 반환함 | 해당 hop에서 내부 TCP 포트까지 도달함 | 피벗 기준 내부 서비스 접근 | 연결 방향과 사용할 listener·protocol 결정 |
| 공격 호스트에서는 `<INTERNAL_IP>:<PORT>`가 실패하고 피벗 호스트에서만 성공함 | 공격 호스트와 피벗 호스트 사이가 터널이 필요한 경계임 | 피벗 호스트 기준 내부 TCP 경로 확정 | SSH, Chisel, Netsh, Meterpreter 중 연결 방향에 맞는 기법 선택 |
| ICMP만 통과함 | 일반 TCP 터널이 제한될 수 있음 | ICMP 통신 경로만 확보 | [[ptunnel-ng ICMP 터널링]] 검토 |
| 외부 DNS 질의만 통과함 | DNS 기반 채널 후보가 있음 | DNS egress 경로 확보 | [[dnscat2 DNS 터널링]] 검토 |
| 내부 CIDR 또는 포트가 확인되지 않음 | CIDR 추정, 방화벽 또는 호스트 역할이 다를 수 있음 | 피벗 경로 미확정 | ARP, hosts, 서비스 설정과 다른 피벗 호스트 확인 |
| 터널 후 공격 호스트 연결만 실패함 | baseline은 유효하므로 터널·프록시·클라이언트 문제일 가능성이 큼 | 피벗 기준 접근만 유지 | listener, protocol, proxy hook, 최종 클라이언트를 분리 점검 |

## 확인할 출력과 권한

| 확인 지점 | 확인할 출력 | 권한 판단 |
|---|---|---|
| 현재 호스트 | `whoami`·`id`, `hostname` | 어느 Identity와 권한의 피벗 세션인지 구분 |
| 네트워크 위치 | NIC, route, 내부 DNS·gateway | 내부 CIDR과 다음 hop을 구분 |
| hop baseline | 피벗 호스트의 `nc -vz <INTERNAL_IP> <PORT>` | 터널을 만들기 전 내부 TCP 도달 가능 여부 확정 |
| 터널 후 비교 | 공격 호스트의 `nc` 체인 로그와 서비스 응답 | 피벗 baseline과 최종 접근을 별도 확인 |
