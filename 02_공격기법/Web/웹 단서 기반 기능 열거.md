# 웹 단서 기반 기능 열거

## 한 줄 판단

현재 명령 실행 위치에서 대상 웹 가상 호스트에 HTTP 요청을 보낼 수 있다면, `robots.txt`, sitemap, `.well-known`, JavaScript, HTML 주석과 과거 URL에서 인증·업로드·API·파일 처리 기능을 찾고 확인된 기능에 맞는 공격기법으로 연결한다.

디렉터리 열거만으로 기능이 충분히 보이지 않거나 SPA/JS·과거 URL·공개 문서에서 API와 파일 처리 단서가 남을 수 있을 때 사용한다. 문자열 후보는 endpoint·권한의 확정 근거가 아니다.

## 전제 조건

| 조건 | 확인 방법 | 충족 기준 |
|---|---|---|
| 콘텐츠 접근 | 브라우저/curl | HTML/JS/robots 조회 가능 |
| 크롤링 대상 | base URL | 링크/폼/API 추출 가능 |
| 비교 상태 | 인증 전·후 또는 역할이 다른 계정 | 요청·응답 차이를 구분 가능 |
| 외부 단서 | 검색 엔진/아카이브 | 과거 URL/문서 후보 |

## 실행

1. `robots.txt`, `sitemap.xml`, `.well-known`를 먼저 본다.
2. HTML/JS에서 URL, API, 주석, endpoint, token과 파일 처리 단서를 찾는다.
3. 폼·JSON body·query·path parameter와 인증 요구 여부를 기록한다.
4. 기능을 인증, 인가, 입력 처리, SSRF, 파일 읽기, 업로드, 제품형 기능으로 분류한다.
5. 실재하는 공격기법만 연결하고, 전용 기법이 없는 항목은 재현 요청과 후보 상태를 유지한 채 웹 상태 라우터로 돌아간다.

### 명령과 확인할 출력

#### 방식 선택

| 현재 확인할 정보원 | 사용할 방식 | 성공 시 얻는 결과 | 실패 시 다음 확인 |
|---|---|---|---|
| 표준 위치의 정적 힌트 파일 | `curl`로 `robots.txt`, `sitemap.xml`, `.well-known` 조회 | 명시된 경로·정책·문서 URL 후보 | 404·리다이렉션·vhost·인증 요구를 구분 |
| 사이트 전체의 링크·기본 메타데이터 | `FinalRecon` | 도구가 접근한 범위의 링크·헤더·기술 단서 | JavaScript 렌더링·인증·접근 차단과 대상 URL 확인 |
| HTML·JavaScript·폼을 크롤링해 관계를 수집 | `ReconSpider.py` | 크롤러가 도달한 URL·폼·스크립트 후보 | 크롤링 깊이, 동일 origin 제한과 인증 세션 필요 여부 확인 |
| 특정 JavaScript 파일을 알고 있음 | `curl`과 `rg` | 코드 문자열에 남은 API·인증·파일 처리 endpoint 후보 | minify·bundle 분할·동적 생성 여부와 실제 URL 접근 확인 |
| XML 설정 파일 후보를 발견함 | `curl`과 `xmllint` | 실제 반환된 XML 구조와 설정 값 | 오류 페이지·HTML 응답, 인증 요구와 XML 형식 오류를 구분 |
| 공개 검색 결과와 과거 URL 단서가 필요함 | 검색 엔진·웹 아카이브 질의 | 현재 사이트에서 보이지 않는 문서·경로 후보 | 검색 결과 시점과 현재 URL 응답을 직접 확인 |
| HTML·JavaScript·DNS·검색 결과에서 S3·Azure Blob·GCS URL을 발견함 | [[공개 클라우드 스토리지 익명 접근 검증]] | 공급자 URL 후보와 정확한 객체·목록의 익명 접근 상태 | URL의 대상 관계와 객체 읽기·목록 권한을 각각 확인 |

정적 파일·크롤러·JavaScript 검색 결과는 URL 후보를 만드는 단계다. 문자열이 발견됐다는 이유만으로 endpoint가 현재 존재하거나 현재 Identity로 접근 가능하다고 판정하지 않는다.

#### 방식 1. 표준 힌트 파일 직접 조회

`<TARGET>`은 요청할 웹 vhost의 IP 또는 FQDN, `<OIDC_ISSUER>`는 discovery metadata의 issuer base URL(경로 포함 가능)이다. HTTP URL과 HTTPS issuer를 임의로 같은 origin으로 취급하지 않는다.

```bash
curl -s http://<TARGET>/robots.txt
curl -s http://<TARGET>/sitemap.xml
curl -s http://<TARGET>/.well-known/security.txt
curl -sS -D - -o /dev/null '<OIDC_ISSUER>/.well-known/openid-configuration'
curl -sS '<OIDC_ISSUER>/.well-known/openid-configuration' | jq '{issuer,authorization_endpoint,token_endpoint,userinfo_endpoint,jwks_uri,scopes_supported,response_types_supported,id_token_signing_alg_values_supported}'
```

확인할 출력:

- `Disallow`, sitemap URL, 연락처·정책 URL과 추가 경로 후보.
- OpenID Provider가 Discovery를 지원하면 `application/json` 문서의 `issuer`, 인증·token·userinfo endpoint, `jwks_uri`와 지원 scope·response type·서명 알고리즘이 보인다. `<OIDC_ISSUER>`에 path가 있으면 마지막 `/`를 뺀 issuer 전체 뒤에 `/.well-known/openid-configuration`을 붙인다.
- metadata의 `issuer`가 요청에 사용한 issuer와 정확히 일치하는지 확인한다. endpoint와 공개 JWK 위치가 보인다는 사실은 사용자 인증 성공, token 발급, 취약한 알고리즘 선택이나 private key 노출을 뜻하지 않는다.
- 빈 출력이면 `curl -i`로 status와 redirect를 확인한다. 404와 인증 요구, 잘못된 vhost를 같은 결과로 취급하지 않는다.

#### 방식 2. 자동 메타데이터와 링크 수집

```bash
FinalRecon --url http://<TARGET>/
```

확인할 출력:

- 실제 요청에 성공한 URL, 헤더, 기술 단서와 도구가 보고한 오류.
- 대상 차단이나 timeout이면 결과 없음으로 판정하지 말고 URL·vhost·TLS·네트워크 경로를 확인한다.

#### 방식 3. 크롤러로 폼·스크립트·URL 수집

```bash
python3 ReconSpider.py http://<TARGET>/
```

확인할 출력:

- 크롤러가 실제 방문한 URL, 폼 field와 JavaScript 경로.
- SPA 렌더링 또는 인증 뒤 기능이 누락되면 브라우저·프록시에서 인증 상태와 동적 요청을 확인한다.

#### 방식 4. JavaScript 문자열에서 endpoint 후보 검색

```bash
curl -s http://<TARGET>/app.js | rg -i "api|auth|login|token|admin|role|upload|download|url|callback|redirect|debug"
```

확인할 출력:

- API endpoint, HTTP method, 객체 ID, URL 입력, 업로드·다운로드 경로와 인증 endpoint 후보.
- 매칭 문자열은 현재 기능 존재나 민감 정보 노출의 증거가 아니다. 관련 chunk 파일과 실제 HTTP 응답을 확인한다.

#### 방식 5. 발견한 XML 설정 파일을 구조적으로 확인

```bash
curl -s http://<TARGET>/<CONFIG>.xml | xmllint --format -
```

확인할 출력:

- XML로 파싱되는 실제 설정 내용과 endpoint·계정 형식·내부 주소 후보.
- 파싱 오류가 나오면 저장된 응답이 HTML 오류 페이지인지, 인증·리다이렉션 응답인지 먼저 확인한다.

#### 방식 6. 검색과 아카이브에서 공개 후보 수집

```text
site:<DOMAIN> filetype:pdf
site:<DOMAIN> intitle:index.of
```

확인할 출력:

- 도메인과 연결된 공개 문서, 디렉터리 목록과 과거 URL 후보.
- 검색 결과는 과거 상태나 제3자 콘텐츠일 수 있으므로 대상 소유 관계와 현재 HTTP 응답을 직접 확인한다.

## 확인할 출력과 권한

- 실제 접근 가능한 URL·API·폼과 코드에 남은 문자열 후보를 구분한다.
- 인증 전·후, 사용자·역할별 status, length, redirect와 응답 body 차이를 함께 기록한다.
- 입력 지점 발견을 인가 우회, 주입, SSRF 또는 파일 읽기 취약점으로 단정하지 않는다.
