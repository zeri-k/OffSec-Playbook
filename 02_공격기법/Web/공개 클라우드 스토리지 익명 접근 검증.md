# 공개 클라우드 스토리지 익명 접근 검증

## 한 줄 판단

조직·도메인과 연결된 S3·Azure Blob·Google Cloud Storage URL 후보가 있다면, 쓰기 작업 없이 정확한 객체의 익명 읽기와 컨테이너·버킷 목록 권한을 분리해 확인하고 공개 범위를 판정한다.

## 전제 조건

| 확인할 것 | 필요한 상태 | 확인 방법 | 미충족 시 다음 확인 |
|---|---|---|---|
| 실행 위치와 경로 | 외부 HTTP(S) 요청이 가능한 작업 호스트 | 후보 URL에 DNS 해석·TLS 연결 가능 여부 확인 | 프록시·vhost·TLS·외부 테스트 위치 확인 |
| 대상 관계 | 후보 URL이 조직 관계와 연결됨 | 대상 페이지·DNS CNAME·공식 공개 문서에서 정확한 URL과 조직 관계 교차 확인 | 공급자 도메인이나 유사 이름만으로 대상 소유를 단정하지 않음 |
| 익명 상태 | cloud CLI profile·cookie·Authorization header를 사용하지 않음 | 새 private browser 또는 자격 증명 없는 `curl` 명령 사용 | signed URL은 별도 권한 위임 자료로 분류하고 URL을 Vault에 저장하지 않음 |
| 요청 범위 | 읽기 전용이고 객체·key 수가 제한됨 | 정확한 객체 URL 또는 작은 `max-keys`·`maxresults`와 prefix 사용 | 버킷 전체 순회·업로드·삭제·ACL 변경은 이 절차에서 수행하지 않음 |

검색 결과, 제3자 색인과 공개 페이지의 문자열은 후보를 만드는 정보원이다. 현재 객체 존재, 조직 소유, 익명 읽기 또는 목록 권한을 그 결과만으로 확정하지 않는다.

## 실행

### 1. 공개 정보에서 공급자 URL 후보 좁히기

조직명이나 도메인을 사용해 검색 결과를 후보 목록으로만 만든다. 검색 연산자 지원과 색인 시점은 제공자에 따라 바뀔 수 있다.

```text
site:amazonaws.com "<ORG_OR_DOMAIN>"
site:blob.core.windows.net "<ORG_OR_DOMAIN>"
site:storage.googleapis.com "<ORG_OR_DOMAIN>"
```

확인할 출력:

- S3 bucket/object, Azure storage account/container/blob, GCS bucket/object 형식을 가진 URL 후보.
- 검색 결과의 제목·snippet·cache는 현재 읽기 성공이 아니다. 실제 URL과 대상 페이지·DNS의 관계를 먼저 확인한다.
- 제3자 색인의 `safe`, `public` 같은 분류는 현재 cloud 접근 제어 설정이나 취약점 판정으로 사용하지 않는다.

### 2. 정확한 객체의 익명 응답 확인

이 block은 자격 증명 없는 분석 호스트에서 실행한다. `<CLOUD_OBJECT_URL>`은 조직 관계가 확인된 한 객체의 HTTPS URL(가상 예: `https://storage.googleapis.com/example-bucket/report.txt`)이고, `<SECONDS>`는 요청 timeout의 작은 양의 정수(가상 예: `10`)다.

자격 증명·cookie·Authorization header 없이 실행한다. 먼저 HEAD로 상태·길이·콘텐츠 형식을 확인하고, HEAD가 허용되며 작은 객체이거나 범위 제한 GET이 가능한 경우에만 1-byte 요청으로 body 읽기를 구분한다.

```bash
curl -sS -I --max-time <SECONDS> '<CLOUD_OBJECT_URL>'
curl -sS -D - -o /dev/null --range 0-0 --max-filesize 1 --max-time <SECONDS> '<CLOUD_OBJECT_URL>'
```

확인할 출력:

- `200 OK`인 HEAD는 해당 URL의 metadata 응답을 받은 상태다. GET의 `206 Partial Content`, 예상한 `Content-Range`와 curl 성공이 함께 확인되면 그 정확한 객체의 1 byte를 익명으로 읽은 상태다.
- 서버가 Range를 무시해 `200 OK`를 반환하면 전송 크기 제한에 걸릴 수 있다. 종료 코드와 `Content-Length`를 확인하고 전체 객체를 읽었다고 기록하지 않는다.
- GCS 공개 객체의 익명 URL은 `https://storage.googleapis.com/<BUCKET>/<OBJECT>` 형식이다. `storage.cloud.google.com`은 공개 객체도 인증을 요구하므로 그 URL의 로그인 응답을 비공개 판정으로 사용하지 않는다.
- redirect, CDN 또는 signed URL이면 최종 host와 만료·서명 query 존재 여부를 구분한다. signed URL 성공은 일반 익명 공개 설정이 아니라 해당 URL이 위임한 제한적 접근이다.

### 3. 목록 권한을 객체 읽기와 별도로 확인

`<S3_BUCKET_ENDPOINT>`·`<AZURE_CONTAINER_URL>`은 이미 식별한 하나의 provider endpoint이며, `<LIMIT>`은 요청 객체 수 상한(가상 예: `10`), `<URL_ENCODED_PREFIX>`는 필요할 때만 넣는 URL-encoded key prefix다. 두 명령은 대안이므로 해당 provider 하나만 사용한다.

목록 조회는 정확한 bucket/container를 이미 식별한 경우에만 작은 제한값과 가능한 prefix를 사용한다. S3 general purpose bucket과 Azure Blob container의 현재 REST 문법만 다루며, GCS 목록은 `storage.objects.list` 권한이 별도로 필요하므로 정확한 공개 객체의 읽기 성공만으로 시도하거나 성공을 추정하지 않는다.

확인할 key prefix가 없으면 아래 URL의 `&prefix=<URL_ENCODED_PREFIX>` 부분 전체를 빼고, `<LIMIT>`에는 요청 수를 제한하는 작은 양수를 넣는다.

```bash
set -o pipefail
curl -sS -D /dev/stderr --max-time <SECONDS> '<S3_BUCKET_ENDPOINT>/?list-type=2&max-keys=<LIMIT>&prefix=<URL_ENCODED_PREFIX>' | xmllint --format -
curl -sS -D /dev/stderr --max-time <SECONDS> '<AZURE_CONTAINER_URL>?restype=container&comp=list&maxresults=<LIMIT>&prefix=<URL_ENCODED_PREFIX>' | xmllint --format -
```

확인할 출력:

- S3 `200 OK`와 유효한 `ListBucketResult`의 `KeyCount`, `Contents` 또는 `CommonPrefixes`는 요청한 범위의 익명 `s3:ListBucket` 허용을 뜻한다. `IsTruncated=true`여도 다음 page를 자동 순회하지 않는다.
- Azure `200 OK`와 유효한 `EnumerationResults`·`Blobs`는 해당 container에서 익명 목록이 허용된 상태다. `NextMarker`가 있어도 이어서 전체 열거하지 않는다.
- Azure의 blob-only 공개 수준은 정확한 blob 읽기를 허용해도 container 목록은 허용하지 않는다. 객체 읽기 성공과 목록 성공을 같은 권한으로 기록하지 않는다.
- S3 객체 요청의 `403`·`404`는 `s3:ListBucket` 권한 유무에 따라 달라질 수 있고, Azure도 계정·container 공개 설정과 요청 version에 따라 `401`·`403` 경계가 달라질 수 있다. 단일 status만으로 객체 존재나 bucket 소유를 확정하지 않는다.

## 관찰과 상태 전환

| 관찰 | 판단 | 결과 상태 | 다음 행동 |
|---|---|---|---|
| 검색·HTML·DNS에서 공급자 URL만 발견 | 소유·현재 상태·접근 권한 미확정 | 클라우드 스토리지 후보 | 대상 관계를 교차 확인하고 정확한 객체 또는 제한된 목록 요청으로 재검증 |
| 정확한 객체가 자격 증명 없이 `206`과 예상 `Content-Range`를 반환하고 1 byte 요청이 성공 | 그 객체의 익명 읽기 확인 | 단일 객체 파일 접근 | 내용은 [[파일 서비스 접근 후 자격 증명과 초기 접근 연결]]에서 자격 증명·서비스·내부 주소 단서로 분류 |
| 제한된 목록 요청이 유효한 S3/Azure 목록 body를 반환 | 해당 bucket/container의 익명 목록 권한 확인 | 객체 key 목록 접근 | 선택한 prefix·개수 안에서 민감도와 정확한 객체 읽기를 별도 확인 |
| 정확한 객체 읽기는 성공하지만 목록은 거부 | 객체 공개와 container 목록 권한이 분리됨 | 단일 객체 파일 접근 | 알려진 객체만 평가하고 전체 storage 노출로 확대하지 않음 |
| `401`·`403`·`404`, redirect 또는 빈 목록 | 인증·공개 설정·URL·객체 존재 중 원인 미확정 | 익명 접근 미확인 | 최종 URL, signed URL, provider endpoint, region·account·container·object 이름과 응답 body의 provider error code 확인 |

익명 객체 읽기나 목록 성공은 쓰기·삭제·ACL 변경, cloud 계정 접근, 다른 객체의 공개 또는 대상 시스템 코드 실행을 증명하지 않는다.

## 영향과 종료

- 위 명령은 cloud 객체·bucket·container 설정을 변경하지 않는다. 공급자·CDN·검색 서비스에는 요청 로그와 사용량이 남을 수 있으며 공격 호스트에서 되돌릴 수 없다.
- 본문을 `/dev/null`로 보낸 명령은 로컬 결과 파일을 만들지 않는다. 별도 파일 저장이 필요하면 작업 전 존재하지 않는 새 고유 경로를 사용하고 [[파일 서비스 접근 후 자격 증명과 초기 접근 연결]]의 분류가 끝난 뒤 그 파일만 보존 정책에 따라 정리한다.
- 이 절차에서는 bucket·container·object 생성, 업로드, 삭제, ACL·IAM 변경으로 쓰기 가능성을 시험하지 않는다.
