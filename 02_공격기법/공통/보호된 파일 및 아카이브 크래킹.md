# 보호된 파일 및 아카이브 크래킹

## 한 줄 판단

분석 호스트에서 읽을 수 있는 SSH private key, Office·PDF, ZIP, BitLocker 또는 생성 조건이 확인된 OpenSSL `enc` archive가 있으면 형식별 hash·복호화 검증 절차로 파일 비밀번호·passphrase를 복구하고, 원본을 열어 내부 credential과 key가 실제로 있는지 확인한다.

RAR·7z·KeePass 등 다른 형식은 설치된 John build의 대응 변환기, 실제 hash 출력과 원본을 변경하지 않는 열기·추출 방법이 확인된 경우에 같은 판단 순서를 적용한다. 이름만 있는 `*2john` 도구 목록을 현재 지원 절차로 간주하지 않는다.

## 사용할 때

- 현재 보유 정보: SMB·NFS·FTP 또는 로컬 파일 시스템에서 암호화된 문서·archive·SSH private key·VHD를 회수했고 파일 출처와 예상 사용자를 알고 있다.
- 명령 실행 위치와 도달성: 보호 파일이 저장된 분석 호스트에서 2john·John·Hashcat을 실행할 수 있으며 오프라인 hash 추출·크래킹에는 원격 대상 접근이 필요하지 않다.
- 현재 가능한 행동과 결과: 보호 파일 자체의 비밀번호나 개인키 passphrase를 복구한 뒤 원본을 열거나 마운트해 내부 사용자명·평문 비밀번호·NT hash·API token·개인키·문서를 확인하며, 파일 비밀번호를 사용자 계정 비밀번호로 간주하지 않는다.

| OpenSSL `enc` 조건 | 생성 당시 cipher, digest, legacy KDF 또는 PBKDF2와 iteration을 구분 | 주변 script·명령 기록·producer 버전 확인 | `Salted__` header나 `file` 결과만으로 조건을 추정해 무제한 조합을 실행하지 않음 |

## 실행

1. 분석 호스트에서 원본 파일 형식·무결성·읽기 권한과 예상 사용자·용도를 확인한다.
2. 원본을 변경하지 않고 형식별 2john 도구로 오프라인 크래킹용 hash를 만든다.
3. John 또는 Hashcat 결과에서 파일 비밀번호·passphrase를 확인한다.
4. 복구한 값으로 원본 파일을 열거나 마운트하고, 내부에서 나온 평문 비밀번호·NT hash·API token·개인키는 연결된 계정과 대상 서비스를 확인한 뒤 별도로 검증한다.

원본과 파생 hash·potfile·restore·결과를 구분하도록 기존에 없는 고유 작업 디렉터리를 먼저 만든다.

```bash
CRACK_ORIGINAL_DIR="$PWD"
CRACK_WORKDIR="$(mktemp -d "${PWD}/protected-crack.XXXXXX")"
```

### SSH key

```bash
ssh2john.py <SSH_PRIVATE_KEY> > "$CRACK_WORKDIR/ssh.hash"
john --wordlist=<WORDLIST> "$CRACK_WORKDIR/ssh.hash"
john "$CRACK_WORKDIR/ssh.hash" --show
```

확인할 출력:

- SSH private key의 passphrase. 이 값은 SSH 사용자 계정의 평문 비밀번호와 다른 결과다.

### Office/PDF/ZIP

```bash
office2john.py <OFFICE_FILE> > "$CRACK_WORKDIR/office.hash"
pdf2john.py <PDF_FILE> > "$CRACK_WORKDIR/pdf.hash"
zip2john <ZIP_FILE> > "$CRACK_WORKDIR/zip.hash"
john --wordlist=<WORDLIST> "$CRACK_WORKDIR/office.hash"
```

확인할 출력:

- 해당 Office·PDF·ZIP 파일을 여는 비밀번호. 파일 내부 credential 존재 여부는 원본을 연 뒤 확인한다.

### BitLocker

```bash
bitlocker2john -i <BITLOCKER_IMAGE> > "$CRACK_WORKDIR/bitlocker.hashes"
grep 'bitlocker\$0' "$CRACK_WORKDIR/bitlocker.hashes" > "$CRACK_WORKDIR/bitlocker-password.hash"
hashcat -m 22100 -a 0 "$CRACK_WORKDIR/bitlocker-password.hash" <WORDLIST> --potfile-path "$CRACK_WORKDIR/hashcat.potfile" --restore-file-path "$CRACK_WORKDIR/hashcat.restore" -o "$CRACK_WORKDIR/recovered.txt" --backend-ignore-opencl -d 1 -O -w 3
```

확인할 출력:

- BitLocker password, 이후 dislocker 마운트 가능.

### OpenSSL `enc`로 암호화된 tar.gz

이 경로는 원천에서 확인된 AES-256-CBC archive를 대표로 하되, 실제 생성 명령이나 같은 producer의 script에서 cipher·digest·KDF 조건을 확인한 경우에만 사용한다. `Salted__` header에는 salt가 있을 수 있지만 cipher·digest·KDF·iteration을 모두 기록하는 container 형식은 아니므로 `file` 결과만으로 `aes-256-cbc`나 PBKDF2 여부를 확정하지 않는다.

먼저 입력과 설치된 OpenSSL을 확인한다.

```bash
file '<OPENSSL_ARCHIVE>'
od -An -tx1 -N16 '<OPENSSL_ARCHIVE>'
openssl version -a
openssl enc -list | grep -F -- '-aes-256-cbc'
```

- ASCII `Salted__`에 대응하는 첫 8 byte `53 61 6c 74 65 64 5f 5f`는 salted `enc` 후보일 뿐 전체 생성 조건은 아니다.
- OpenSSL 3.x의 현재 기본 digest는 SHA-256이고 `-pbkdf2`의 기본 iteration은 10000이지만, 오래된 파일이 같은 기본값을 사용했다고 소급하지 않는다. `-iter`는 PBKDF2를 활성화하며 암호화 때와 같은 salt 길이·digest·iteration이 필요하다.
- 생산 조건을 알 수 없으면 이 절차의 입력 미충족으로 남기고 archive를 손상·비밀번호 오류로 확정하지 않는다.

원천 파일과 분리된 고유 작업 디렉터리에서 한 profile만 선택한다. PBKDF2로 생성된 파일이면 첫 번째 배열을, legacy password KDF로 생성된 파일이면 두 번째 배열을 사용한다. `<DIGEST>`와 `<ITER>`는 확인한 생성 조건으로 바꾼다.

```bash
OPENSSL_CIPHER='-aes-256-cbc'
OPENSSL_KDF_OPTIONS=(-pbkdf2 -iter <ITER> -md <DIGEST>)
# legacy enc 파일인 경우에만: OPENSSL_KDF_OPTIONS=(-md <DIGEST>)

test ! -e "$CRACK_WORKDIR/openssl-candidate.tar.gz"
test ! -e "$CRACK_WORKDIR/openssl-decrypted.tar.gz"
test ! -e "$CRACK_WORKDIR/openssl-recovered.pass"
```

후보를 shell word splitting하지 않고 한 줄씩 읽는다. OpenSSL 복호화 성공만으로는 CBC padding 오탐이 가능하므로 gzip integrity와 tar member 목록까지 모두 성공한 후보만 유지한다.

```bash
while IFS= read -r OPENSSL_CANDIDATE || [ -n "$OPENSSL_CANDIDATE" ]; do
  rm -f -- "$CRACK_WORKDIR/openssl-candidate.tar.gz"
  if printf '%s\n' "$OPENSSL_CANDIDATE" | \
       openssl enc -d "$OPENSSL_CIPHER" "${OPENSSL_KDF_OPTIONS[@]}" \
         -in '<OPENSSL_ARCHIVE>' -out "$CRACK_WORKDIR/openssl-candidate.tar.gz" -pass stdin 2>"$CRACK_WORKDIR/openssl.err" &&
     gzip -t "$CRACK_WORKDIR/openssl-candidate.tar.gz" &&
     tar -tzf "$CRACK_WORKDIR/openssl-candidate.tar.gz" > "$CRACK_WORKDIR/openssl-members.txt"; then
    mv -- "$CRACK_WORKDIR/openssl-candidate.tar.gz" "$CRACK_WORKDIR/openssl-decrypted.tar.gz"
    printf '%s' "$OPENSSL_CANDIDATE" > "$CRACK_WORKDIR/openssl-recovered.pass"
    chmod 600 "$CRACK_WORKDIR/openssl-recovered.pass"
    break
  fi
done < '<WORDLIST>'

test -s "$CRACK_WORKDIR/openssl-decrypted.tar.gz"
test -s "$CRACK_WORKDIR/openssl-recovered.pass"
```

확인할 출력:

- `openssl-decrypted.tar.gz`, 비어 있지 않은 member 목록과 mode 600의 복구 passphrase 파일이 함께 있어야 후보 검증 성공이다.
- `bad decrypt`는 password뿐 아니라 cipher·digest·KDF·iteration 불일치일 수 있다. 후보 목록만 늘리기 전에 producer 조건을 다시 확인한다.
- `gzip -t` 또는 `tar -tzf` 실패는 복호화 성공으로 기록하지 않는다.

추출 전 절대 경로·`..` traversal과 link·device·FIFO member를 별도로 확인한다. 출력이 하나라도 있으면 자동 추출하지 않는다.

```bash
grep -nE '(^|/)\.\.(/|$)|^/' "$CRACK_WORKDIR/openssl-members.txt"
tar -tvzf "$CRACK_WORKDIR/openssl-decrypted.tar.gz" > "$CRACK_WORKDIR/openssl-members.verbose.txt"
awk '$1 ~ /^[lhbcp]/ { print }' "$CRACK_WORKDIR/openssl-members.verbose.txt"
```

두 검사 출력이 비고 새 extraction directory가 만들어진 경우에만 owner·mode를 현재 사용자로 제한해 추출한다.

```bash
install -d -m 700 "$CRACK_WORKDIR/openssl-extracted"
tar -xzf "$CRACK_WORKDIR/openssl-decrypted.tar.gz" \
  -C "$CRACK_WORKDIR/openssl-extracted" --no-same-owner --no-same-permissions --keep-old-files
find "$CRACK_WORKDIR/openssl-extracted" -maxdepth 2 -printf '%M %u:%g %p\n'
```

## 확인할 출력과 권한

- hash 추출, 비밀번호 복구, 파일 열기 또는 마운트 성공을 각각 확인한다.
- 보호 파일 접근 권한은 내부 credential이 가리키는 계정 권한과 동일하지 않다.
- SSH key나 VHD를 사용할 때 실제 사용자와 접근 가능한 파일 범위를 별도로 확인한다.
- 보호 파일 비밀번호·SSH key passphrase, 파일 내부의 평문 계정 비밀번호와 private key 자체를 서로 다른 값으로 기록한다.

## 변경 영향과 정리

`*2john`은 파생 hash 파일을 만들고 John·Hashcat은 복구 평문, potfile과 중단 session을 저장할 수 있다. 위 Hashcat 명령은 이를 전용 작업 디렉터리로 제한한다. John Jumbo에서 작업별 pot 경로를 사용할 때는 설치된 build의 `john --list=hidden-options`에서 `--pot` 지원을 확인한 뒤 같은 디렉터리를 지정한다. 지원 여부를 확인하지 않고 shared `john.pot`을 삭제하거나 다른 작업의 복구 결과를 지우지 않는다.

원본 보호 파일과 wordlist는 이번 절차가 만든 자원이 아니다. 분석이 끝난 뒤 보존하지 않을 파생 파일만 정확한 경로로 제거한다.

```bash
rm -f -- "$CRACK_WORKDIR/ssh.hash" "$CRACK_WORKDIR/office.hash" "$CRACK_WORKDIR/pdf.hash" "$CRACK_WORKDIR/zip.hash"
rm -f -- "$CRACK_WORKDIR/bitlocker.hashes" "$CRACK_WORKDIR/bitlocker-password.hash"
rm -f -- "$CRACK_WORKDIR/hashcat.potfile" "$CRACK_WORKDIR/hashcat.restore" "$CRACK_WORKDIR/recovered.txt"
rm -f -- "$CRACK_WORKDIR/john.pot"
find "$CRACK_WORKDIR/openssl-extracted" -depth -delete 2>/dev/null
rm -f -- "$CRACK_WORKDIR/openssl-candidate.tar.gz" "$CRACK_WORKDIR/openssl-decrypted.tar.gz"
rm -f -- "$CRACK_WORKDIR/openssl-recovered.pass" "$CRACK_WORKDIR/openssl.err"
rm -f -- "$CRACK_WORKDIR/openssl-members.txt" "$CRACK_WORKDIR/openssl-members.verbose.txt"
cd -- "$CRACK_ORIGINAL_DIR"
rmdir -- "$CRACK_WORKDIR"
test ! -e "$CRACK_WORKDIR"
```

`rmdir`가 실패하면 재귀 삭제하지 말고 예상하지 않은 hash·session·복호화 산출물을 확인한다. shared John potfile을 사용했다면 파생 파일 정리만 확인할 수 있으며 복구 평문의 shared cache 잔여 영향은 미정리로 기록한다. 원본에서 복호화 파일을 별도로 만들거나 archive를 추출했다면 새 경로와 기존 부재를 기록한 경우에만 그 exact 산출물을 추가로 제거한다.
